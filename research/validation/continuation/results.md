# Результаты следующего этапа

**13 ноября 2026 г.** В лаборатории замкнут путь одного синтетического события: запись в PostgreSQL → отправка настоящим серверным логгером → локальный SignalR → штатная подписка ApiClient → обработчик ViewModel → строка настоящего EventLogControl в Xvfb. Успех чтения на развёрнутом Management API с учётной записью продукта остаётся открытым. Реестры прежних наблюдений и выводов сохранены. ## Варианты и диагностическая запись

Для каждого из пяти различных managed-образов отдельно декодированы все 13 методов SpecterInsight.Logging.LogEntry: восемь аксессоров и пять конструкторов. Аргументы, сигнатура, IL, токен, MVID и SHA-256 тела приведены на каждый вариант. Аксессоры непосредственно читают и записывают поля System, Message, TimeStamp и Count. В каждом конструкторе начальное значение Count равно 1. Пустой конструктор оставляет строки null и время по умолчанию. Конструктор с system, message и timestamp переносит переданные значения. В вариантах конструктора без system есть обращение к источнику имени компьютера, а без явной метки времени — к UTC-часам, кроме пустого конструктора. У методов отсутствуют собственные области обработки исключений. [Карточки по хешам](diagnostic-variants.json)

Динамически в каждом образе проверены начальные значения, три значения message (null, пустая строка, текст) и обратное чтение после установки Count в −1 и смены сообщения. Два запуска дали одинаковые результаты. У серверного образа проверена связь с исходным документом Logging/LogEntry.cs для **каждого из 13 методов**: идентификатор PDB, хеш исходника и первая видимая точка IL/строка. У четырёх остальных сборок приёмка опирается на их собственный IL и исполнение DTO. У двух конструкторов с обращением к окружению поведение этого обращения известно только по статическому вызову. Выполнялся исключительно диагностический класс. [Журнал](diagnostics/logentry-1.jsonl) · [Повтор](diagnostics/logentry-2.jsonl)

Восемь разных нативных файлов и 22 модуля получили отдельные записи. Для PE сохранены DLL/EXE, архитектура, количество секций, наличие каталога сертификатов, типы отладочных записей и имена импортируемых библиотек. Для модулей — MVID, собственная версия и кандидаты по совпадению имени и версии AssemblyRef. Такие кандидаты нашлись у семи модулей среди отобранных сборок. Фактическая загрузка модулей остаётся Unverified. [Карточки вариантов и модулей](variants-and-modules.json)

## Сервер и административный HTTP

В асинхронном пути Host обнаружен вызов KestrelManagementServer.Build. Последующие перегрузки ведут к трём телам Build. В MoveNext с токеном 0x06001bf3 видны ConfigurationBuilder.Build (IL +15) и передача управления следующему Build (+28). В теле 0x06001bf5 видны AddTransient для EventLoggingService (+822), AddScoped для пары IDocumentationService/DocumentationService (+2040) и WebApplicationBuilder.Build (+2671). В DocumentationController конструктор требует службу документации и состояние индексирования; в SearchDocumentation вызов службы подтверждён операндом +126 в автомате 0x0600272b. Для аудита потребление DatabaseService и контекста рассылки дополнительно подтверждено исполнением LogAsync. Прямой переход из обследованных тел Build в отдельный класс Startup не установлен. Фактический порядок разбора значений на действующей установке остаётся открытым. [Операнды и координаты IL](administrative-call-sites.json)

| Действие DocumentationController | Клиент, относительный маршрут | Вывод в границах проверки |
|---|---|---|
| GetAllDocumentation | DocumentationAsync, GET /Documentation | На настоящем MVC-маршруте собственный фильтр продукта дал 401. Проверены реальный запрос штатного клиента и его ApiException. |
| SearchDocumentation | SearchAsync, POST /Documentation/search | Штатные действие, сервис, ApiClient и PostgreSQL дали ожидаемый заголовок по запросу Cherries на стендовом маршруте. Провайдер векторов возвращал пустой массив. Наблюдалась резервная ветвь поиска подстроки. |
| GetIndexStatus | IndexStatusAsync, GET /Documentation/index-status | Статически установлено чтение состояния индексирования. HTTP-ответ на действующей установке не проверен. |
| GetEmbeddingProviders | EmbeddingProvidersAsync, GET /Documentation/embedding-providers | Установлены соответствие клиентского вызова и объявленный маршрут чтения списка. Доступность конкретных провайдеров не проверена. |
| StartIndexing | IndexAsync, POST /Documentation/index | Команда запуска индексирования меняет состояние. Классификация статическая; HTTP-вызов команды в этом опыте не выполнялся. |

Положительный HTTP-контроль использовал отдельный адрес /reference/Documentation, на котором стенд вызывал штатный Load. Проверены 200, вложенный DTO и пустой массив. Прочитанные через сокет данные сравниваются с первой фикстурой документации. На /errors/Documentation проверена реакция клиента на 503. Для штатного маршрута получены два отказа: без личности и с синтетической личностью ASP.NET. Подтверждение положительного доступа потребует штатной учётной записи эталонной установки. ## Экран, потеря соединения и корреляция

DocumentationViewer.OnAttachedToVisualTree вызывает UpdateDocumentation. У вызываемой ViewModel используется Globals.Client. Xvfb-прогон с контролируемым HTTP-ответом показал текст Fixture Page в видимом элементе штатного визуального дерева. В том же открытом окне после 503 ранее загруженная страница осталась на экране; при успешном пустом ответе она исчезла. Отдельный свежий экран с 503 сохранил неинициализированную коллекцию. У события после принудительного обновления и 503 существующая строка также сохранилась. Пустой успешный ответ очистил журнал. Повторное открытие и обновление снова показало строку. Это измерения открытых контролов, видимости и размеров элементов в Xvfb. Пиксельная идентичность внешнего вида и штатная навигация главного окна не проверялись. [Журнал экранов](desktop/desktop-1.jsonl) · [Независимый повтор](desktop/desktop-2.jsonl)

В отдельном опыте сервер и окно работали одновременно. Штатный EventLoggingService записал **fixture-live-window** в чистую PostgreSQL 16.4 и передал его настоящему HubLifetimeManager через IHubContext стендового узла. В другом процессе штатный ApiClient.OnEventNotification зарегистрировал подписку на предоставленное стендом соединение. Стенд связал эту подписку со штатным EventLogViewModel.OnEventNotification. В коллекции найден тот же id, на экране — уникальный текст Synthetic audit fixture-live-window, в SQL — одна запись с этим id. Для этих четырёх границ не использовался промежуточный файл данных. Полное подключение оригинального клиента к оригинальному хосту, выбор хаба при входе и поведение после штатного восстановления соединения остаются за границей опыта.

Для отдельного наблюдателя, явно остановленного и снова запущенного, все три записи online/offline/reconnected сохранились в БД. Первым сообщением после повторного подключения пришло reconnected. Из этого не следует отсутствие более поздней синхронизации истории приложением. [Контрольный прогон передачи](loopback/loop-2.jsonl)

## Вспомогательные компоненты и пробелы

Для CSV расхождение доведено до потребителя. Штатный LoadVendors прочитал строку с полем «Example, Incorporated», ApplyHelper дополнил синтетический объект данных полем MacAddress_vendor со значением «Example». Это подтверждение преобразования данных. Представление именно этого поля в UI не исследовалось. Для поиска путь прошёл от DTO ApiClient через HTTP-адаптер и штатное действие до DocumentationService, PostgreSQL и возвращённого DTO. Положительный пример относится к резервному поиску; векторная модель проверялась ранее отдельно. [Наблюдения стенда](loopback/loop-1.jsonl)

Сверка текущего дерева с сохранённым манифестом по именам кандидатов в сетевые захваты не выявила нового источника. Для канала Specter–Server остаётся прежний статус Unverified. Для истории миграций и состояния развёрнутой БД нет эталонной выгрузки. Для Kibana и GeoIP действуют прежние границы: проверены структура экспорта и геобаза, установка и фактический внешний сервис не наблюдались. Для notebooks и скриптов сохранена статическая атрибуция, для трёх зашифрованных вложений — только внешние идентификаторы.
